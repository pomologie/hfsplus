# Deterministic HFS+ write-once constructor (H-BUILD-01 through H-BUILD-05)

Purpose: produce finalized valid raw HFS+ volume from a logical manifest with no mutable-mount simulation and no full intermediate image. Initial profile clean nonjournaled HFS+; qualified HFSX later. Reader and writer share codecs/format model, but tests use independent readers and native tools. No complete journaling engine required to format clean volume. Inputs are generic streams and metadata, not host-specific path walking. Use typed geometry, capacity policy and immutable source lengths. Bound payload independently of file size; metadata scales with entries/extent count and is separately budgeted. `PlanDraft -> SealedPlan` per C3; no hidden reallocation after seal.

## Case-sensitive HFSX construction

Set `VolumeOptions::format` to `VolumeFormat::HfsX` to seal a clean, nonjournaled HFSX version 5 volume. Catalog paths still use historical canonical decomposition. Binary comparison of the stored UTF-16 units determines collisions, parent lookup, and catalog order. Case variants and names containing distinct ignorable characters stay distinct. HFSX folders record direct subfolder counts, and the regular hard-link backing directory sorts before the ordinary root entries. `VolumeOptions::new` and `VolumeOptions::for_capacity` default to case-folded HFS+. [Apple TN1150](https://developer.apple.com/library/archive/technotes/tn/tn1150.html#HFSX)

The HFSX fixture for H-FMT-03 and H-BUILD-02 compares complete raw images from opposite manifest orders and checks the primary and alternate headers, catalog ordering, folder counts, and shared hard-link identity. The 8 MiB fixture had SHA-256 `14bd7cfd640f004b04d5a60f3548812c9b036f337b16f4e48e2a7d4e087b1c50`. On arm64 macOS 14.7.2 (23H311), 7-Zip 17.05 identified HFSX and extracted both case-distinct payloads byte for byte. Apple `hdiutil` identified `Apple_HFSX`, verified the UDRO container, and exported the identical raw disk. Read-only attachment returned `Device not configured` on this runner. Native filesystem checking and mounted metadata remain open for this constructed profile. [Construction fixture](../../crates/filesystem/hfsplus-builder/tests/hfsx_volume.rs)

## Planning algorithm

1. Validate tree, types, names, source identities and declared lengths, hard-link equivalence, required metadata, unique canonical paths and parent relationships. Reserve generated asset entries before identity freeze; reject special namespace and illegal collisions. Validate volume label and geometry selection. Determine deterministic epoch/volume identity, root and other reserved CNIDs, allocate stable CNIDs in comparator order with matching thread records. Assign deterministic valid link refs for hard links, construct private metadata records under format constraints. Return identity registry so caller can generate background aliases and Finder stores. Generated payload lengths bound, freeze metadata only after finalization.
2. Compute total payload lengths (data/resource forks, large attributes) and fixed special metadata. Choose allocation block size, node sizes and clump policy based on qualified defaults and volume size; explicit overrides validated. Align each extent and reserve header/alternate sectors. Use checked capacity estimates then iterate deterministic layout to stable exact sizes: catalog keys/records, extents overflow entries (including all needed forks), attributes keys/records, node map and allocation bitmap sizes depend on geometry. Use capped iteration, monotonic growth of reservations or proof of convergence; if unable, typed `LayoutUnstable`, not truncated output. Avoid self-referential extents tree bootstrap by placing metadata in known contiguous regions in initial profile. Plan supports max 32-bit allocation block count and representable fork/file lengths. `size=auto` chooses minimum qualified volume + explicit free space; explicit size errors if inadequate, no shrink by mutating finished volume. Do not infer macOS default sizing from fstool. Reserve unused blocks as zero. Large volumes/huge metadata may need optional metadata spool; limits explicit.
3. Bulk-build each B-tree: sort records with correct comparator and key lengths, pack leaf records into chosen nodes using exact offset table overhead and alignment; split before overrun, preserve ascending keys, fwd/back chain. Generate upper index levels with proper separator keys/child pointers; build header, map nodes and allocation bits; compute counts/root depth and verify every node within fork. Ensure index can fit maximum key plus pointers and minimum required fanout. Handle empty trees with valid header representation (qualify against native fixture). Plan extents and metadata storage, produce catalog threads, extent records, attr records, hard link metadata and counters. Avoid incremental insertion for whole-tree builds; preserve explicit known allocation and xattr streams.
4. Allocate non-overlapping aligned extents for metadata and each fork. Use deterministic placement, coalesce contiguous extents, avoid fragments in default; overflow extents encode when needed. Compute file logical vs allocated size, zero pad final allocation block, exact allocation bitmap from owned block ranges (no marking intentional free blocks used), free count, next allocation, file/folder counts/valence, root Finder fields, primary/alternate volume headers, clean state, nonjournaled flags and consistent write count as qualified. Do not label journaled if no journal. Verify full allocation coverage and no overlapping data owners except deliberate shared link representation. Seal an interval map covering volume, each interval `MetadataBytes`, `SourceSlice`, `Zero`. Metadata builder outputs owned records not raw disk; no filesystem mutation after seal.
5. `read_exact_at` splits ranges, reads only relevant source bytes; known zeros filled without backing allocation. Iterator streams ascending blocks; `write_to(Write)` produces raw image, optionally sparse-file sink hole creation only on supported platforms and semantic zeros guaranteed. All output exactly planned length. Verify source identity before/after reads, short/changing data failure, use immutable snapshots when strict deterministic assurance needed. Source reader interfaces need no std for core; desktop source handles in adapters. Thread-safe read where supported, serial fallback. dmgez consumes plan directly as raw source and does UDIF compression; filesystem never sees codec details.

## Verification and acceptance

Native tests generate comparable newfs_hfs/ditto fixtures and check our raw volume with read-only fsck then mount on disposable test device, compare tree, metadata, forks, file counts, link semantics. Tests raw reader independently checks output, fstool/hfsplus reader comparison when profile supported. Fixtures: empty volume, zero-byte file, many small files requiring multi-level catalog/map nodes, multi-GiB file, large xattr requiring fork, resource fork, symlink, hard link group, decomposed collision, max-name, generated root Finder info and IDs, exact-capacity and insufficient space, final alternate header offsets, deterministic seed, source changed mid-read, concurrent sector reads, bounded nonseekable sink, corrupt allocation and overflow checks. Raw image byte identical across runs and supported hosts given identical logical manifest/profile; no claim Apple byte-identical allocator. Add property tests ranges cover exactly and do not overlap, bitmap counts match planned allocations, all file data read back. Large-scale benchmark metadata budget and no full raw intermediate in dmgez integration. Default constructor emits only qualified profile; unsupported journaling, sparse semantics, names, timestamp or metadata require explicit error/loss report. Hard links preserved or fail, not flatten silently. Add HFSX profile after comparator parity. P0 release does not need mutable writes, repair or resizing.
