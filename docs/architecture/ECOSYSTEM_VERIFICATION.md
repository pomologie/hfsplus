# Ecosystem verification standard (EVS-1, proposed)

Correctness and preservation of user data outrank feature count and speed. This standard applies independently to dmgez, hfsplus and apfs. It carries forward ExaCopy's verification-first engineering and the supplied Euclid 2.0 four-layer strategy, with storage-specific additions. A proof of a model is not a proof of the entire program. A native mount, signature check, format round trip, coverage percentage or successful fuzz campaign alone is not a correctness certificate.

## 1. Assurance layers and adoption

| Layer/tool | Scope | Gate |
|---|---|---|
| Rust compiler, fmt, Clippy, nextest | Typed states/units, unit/integration/doc tests | Every PR from bootstrap; doctests run separately where nextest does not run them |
| rstest, insta | Parameterized profiles, stable semantic reports and diagnostics, normalized UI snapshots | Required where applicable; snapshots reviewed, not auto-approved |
| proptest, state-machine proptest | Arithmetic, packing, range maps, allocators, trees, operation histories, reference models | Required for critical code at first release |
| cargo-fuzz / libFuzzer | All untrusted format entry points, decompression, XML/plist, config, paths | Smoke/replay on PR, longer scheduled/release campaigns |
| cargo-llvm-cov | Line, region and function coverage by crate/profile; branch metrics where available | Required report; critical paths and all invariants have tests |
| cargo-mutants | Test sensitivity, including comparison/overflow/branch/error mutants | Scheduled and critical-module changes/release; disposition survivors |
| Kani | Actual Rust checked arithmetic, slices, bounds, map search, transition logic | Small safety-critical obligations required before first affected release; broader coverage incremental |
| Lean 4 + Mathlib + hax/Charon/Aeneas | Mathematical specifications and implementation-linked proofs for supported pure Rust | Early pilot; selected obligations required at registered maturity milestones, comprehensive proof not MVP blocker |
| TLA+ / TLC | Finite protocol models: ordered compression, publication, mount/eject, journal, CoW commit, recovery | Required for mutable filesystem or other high-risk protocol gates as cataloged |
| Loom | Exhaustive exploration within bounds of instrumented Rust synchronization | Required for custom concurrency primitives and selected scheduler/cache state |
| Shuttle | Seeded schedule exploration/replay of larger Rust state machines | Targeted, scheduled and failure reproduction; not exhaustive proof |
| Miri | Undefined behavior and aliasing on supported Rust paths | Scheduled and targeted PRs for unsafe/pointer changes; excluded FFI paths recorded |
| mockall, hand-written fault devices | Adapter failures, deterministic block I/O, source/sink mutation | Required for error-handling and durability paths |
| Wiremock, Toxiproxy | HTTP range/notary mock protocol, interruptions, latency, resets, malformed responses | Only optional network integrations; no service deps in default build |
| Testcontainers | Disposable integration infrastructure when a service is actually needed (HTTP fixture server, proxies, etc.) | Evaluate per optional service; no PostgreSQL/SQLx/Goose requirement for these tools |
| Criterion | Controlled throughput, CPU, memory, size and latency regressions | Baseline at working implementation; scheduled and release controlled hosts |
| Native macOS oracles + independent implementations | Actual on-disk semantics and observable behavior | Mandatory for every advertised native format/profile, independently of proofs |

Tooling versions are pinned and checks run in isolated development/CI jobs, never pulled into normal release binaries. `cargo-nextest` is mandatory for Rust test jobs, not optional. No global nightly MSRV: production stable, Kani/Miri/fuzz/extraction toolchains pinned separately. Tools that cannot run on all OSes have a Linux verification lane plus platform-native tests. Record unsupported target/tool combinations, not silent skips. Evaluate Verus or Creusot as alternatives if extraction does not support a critical Rust subset; no mandate to maintain three proofs of the same property. Any change of proof technology records the claim preserved, trusted assumptions, and replacement evidence.

## 2. Design for verification

- Pure checked functions on owned value types and bounded slices; no transmuting hostile bytes into Rust layouts. Newtypes prevent mixing byte offsets, logical sectors, allocation blocks, object IDs and transaction IDs. Arithmetic checked before conversion/allocation, not after. Error on overflow, impossible geometry or resource limit. Endianness explicit. Fallible parsing never panics on malformed data. Avoid unsafe; format/allocator/geometry/model modules forbid unsafe where possible. Platform FFI is small, isolated and reviewed. No undocumented `unwrap`, `expect`, indexing, unchecked casts, wrapping arithmetic or unchecked recursion on untrusted paths. Intentional wrapping (e.g. checksum) documented and tested.
- Separate pure planner/state-transition functions from I/O executor. State transitions produce an explicit ordered effect list; interpreter validates and performs effects; deterministic simulation supplies alternate device, clock, scheduler and transport. Production code is the system under test, not a parallel toy implementation. A simple slow reference model uses different algorithms (sorted maps, explicit sets of blocks, raw byte arrays) and is limited to small sizes. Compare after every generated operation and restart, including failure outcomes, not just final output. Never import reference helpers into production.
- Immutable draft/sealed types; immutable view ID includes selected filesystem version/XID. Mutating APIs require exclusive capability, typed transaction states and explicit commit/durability contracts. A source identity change invalidates a plan. No implicit stale cache trust, path traversal, guessed metadata, or use of live host volumes in tests.
- `tests/support` or internal `testkit` packages, no runtime dependencies on harness. Each repo owns independent raw-storage and reference-model tests. If a stable general-purpose block fault/simulation library emerges, extract as its own repo only when actual reuse justifies it. No new shared production repo required initially.
- Keep Rust source files within the project's 500-line convention by default (physical lines; generated code, fixtures, intentionally cohesive tables and exceptional modules need documented per-file reasons). Deterministic check with an exception list; no arbitrary splitting of cohesive functions just to satisfy a number. Prefer more meaningful verification/test code than production code where warranted; neither line count nor coverage alone determines quality. Count generated code separately. Coding agents must not weaken invariants, mark TODOs as verified, reduce a proof bound, change oracle values, relax a test or accept new snapshots without review and reason.

## 3. Requirements, invariants, proof obligations and evidence

Each repository has `docs/reference/requirements.json`, `test-catalog.json` and `verification/obligations.json`. Requirement IDs are stable. A proof obligation names the invariant, requirement IDs, scope, proposed target, assumptions, a concrete property, evidence methods, finite bounds where appropriate, gate milestone and negative witness. Each obligation is planned until implementation exists and evidence is produced. A gate may require multiple evidence methods, not whichever is easiest. The obligation activation release can be later than the requirement's first test-qualified release. Scope a gate by capability/profile, not global version comparison. All mandatory tests and activated mandatory obligations must pass for that profile. Other open obligations appear in the public limitations and cannot be advertised as proven. Do not defer a known corruption or security failure as merely an unproved theorem.

Evidence record per actual invocation: repository commit + dirty flag, selected target/function and source hash, feature set, profile/fixture manifest digest, Rust/compiler/tool version/runner OS and hardware model where relevant, proof extraction inputs and hashes, exact command/arguments and tool config, assumptions/bounds, seed/schedule, result, duration, exit code, diagnostic/artifact digest. Use `verification/evidence.schema.json` (shared template) as initial contract. No secrets/absolute private paths in public logs. Store full logs and minimized inputs by hash; link to CI artifact and immutable release report. Pin external oracles and codec versions; refresh expected fixture facts independently when upstream changes. Distinguish `planned`, `not_run`, `pass`, `fail`, `timeout`, `unsupported`, `unavailable`, `inconclusive`. Only `pass` for the exact required scope satisfies a gate. A valid proof of a mathematical statement is different evidence from proof of production Rust equivalence; a bounded pass is not unbounded proof. If code, enabled feature set, assumptions, proof, oracle, or dependency changes, invalidate affected evidence and regenerate. No copying old passing badges across commits without dependency-impact justification and reproducible provenance.

## 4. Proof workflow and trusted computing base

Lean specifications use mathematical natural/integer arithmetic (then prove conversion to machine arithmetic), explicit interval/sequence/map abstractions, separate physical and logical address namespaces, allocation conservation, sortedness, nonoverlap and total coverage, monotonic commit state, snapshot reachability, exact read semantics. State all preconditions and prove they are checked at the call boundary; never assume the very property intended to prove. A separate handwritten Lean model is a useful spec, not a claim about shipped Rust. Preferred production bridge: hax 0.4.x or a later qualified pinned version orchestrates Charon extraction to LLBC and Aeneas translation to Lean. The current hax `lean` backend uses Charon/Aeneas (not its legacy extraction engine); pin compatible Rust, hax/hax-lib, Charon, Aeneas and Lean toolchain, Mathlib and generated external models. Verify the exact CLI for the pinned release; `cargo hax into lean` is the current entry point. See sources V01-V03. Keep functions small, safe, sequential and deterministic; treat external codecs, OS, FFI, I/O and concurrency as explicit contracts not magically verified. External models are part of the trusted computing base, reviewed and tested; no invented axioms about correctness of parser, hardware or codec.

Suggested repository layout (create when corresponding gate is implemented):

```text
verification/
  obligations.json            # canonical scope, method, gate and requirement links
  assumptions.md              # per-model and theorem assumptions, trust register
  evidence.schema.json        # results metadata contract
  kani/                       # harness inventory; actual harnesses adjacent to Rust or dedicated test target
  models/                     # TLA+ specs, TLC cfg, bounded reference transition models
  proofs/lean/
    lean-toolchain
    lakefile.toml
    lake-manifest.json
    Specifications/           # independent mathematical model
    Extraction/               # generated from actual shipped Rust, never hand-edited
    Verification/             # refinement/equivalence and property theorems
    Assumptions/              # explicit external contracts with tests
  corpus/                     # minimized counterexamples and regressions (license reviewed)
```

Proof job: regenerate extraction from the pinned source/target/features, diff/hash generated artifacts, compile with Lean `lake build`, make warnings/placeholders in the required theorem dependency closure fatal, audit `#print axioms` or equivalent theorem axiom inspection. No `sorry`, `admit`, hidden `sorryAx`, unreviewed axioms, or replacement stubs in required closure. Standard Lean foundations and reviewed external assumptions recorded; unsupported extractions remain unsupported. CI verifies theorem identifiers and trace to exact function/feature hash. Pin/lock proof dependencies and reject hand edits to extraction. Counterexamples from model/proof become tests. Pilot checked region containment and canonical packing first, then expand. Kani: actual functions called by harness; nondeterministic bounded inputs, constrained by only documented preconditions, assertions on result/error and postconditions. Verify loop unwinding adequacy (unwinding assertions), no suppression of overflow/panic checks, reachability/cover for success and failure paths and non-vacuity. Record max input length, count, widths and unwind bound per harness; use full machine-width scalar inputs where possible. Mutation of critical predicates must be detected by at least one test/proof; a proof that also accepts a known bad mutation is rejected.

TLA+/TLC: explicit Init/Next and invariants, crash/restart actions, volatile/durable split, finite domains, fairness only for documented liveness (e.g. responsive device/scheduler, no infinite crash). Check deadlocks unless termination is explicitly allowed; record bounds, states/distinct states, constraints, worker configuration and counterexample trace. No safety claim outside explored model unless separately proved. Link abstract action to production event/action via trace adapter; replay model counterexamples in actual Rust tests; compare implementation traces with model after each abstract step. Model check protocols before first deployment of mutable/safety-critical functionality; stronger invariants and bounded simulation do not remove native tests. Loom/ Shuttles exercise actual instrumented synchronization or explicit scheduling adapters; model Rayon scheduling via our admission/order coordinator, not claiming to exhaustively verify Rayon's internals. Test with real Rayon pools and resource pressure as well.

## 5. Deterministic simulation and storage failure apparatus

`FaultDevice` wraps a byte/block store with separate volatile and durable layers, writes/barriers tracked by sequence ID, legal atomic granule, alignment, size and device capabilities. Reads can be short/interrupted/errors; writes can fail before or after partial persistence, be reordered within a barrier epoch, be torn by granule, duplicated or lost on crash if unflushed. Flush may fail or have uncertain outcome. Honor only the persistence model promised by the chosen backend; dishonest device/firmware and arbitrary corruption are not solved by a journal proof. A separate adversarial corruption mode flips/truncates bytes or changes identity and expects safe diagnostic, not necessarily repair. Start with in-memory small explicit block maps, then sparse file-backed large cases and native test volumes. Never use a real disk as failure-injection target. Record RNG (algorithm/version), seed, fault schedule, device geometry, operations, expected committed state, actual recovered state, trace and minimized reproduction. A simulated crash drops volatile state and reopens using a fresh instance; not merely call a rollback method on the same object. Also kill a child process at cut points on disposable files; distinguish process crash from power loss. Use instrumented barriers and enumerate every persistent write and flush boundary, small exhaustive subsets/permutations of outstanding writes and torn granules, then randomized larger histories. Test double-crash during recovery and repeated recovery idempotence.

Invariants by operation:

- Immutable construction: no write to input; published output is prior valid artifact or new completed artifact (visibility/atomicity under qualified platform replace primitive). Sync file data and directory metadata where supported before claiming durability. Failed caller-owned stream explicitly invalid; cannot roll it back. Crash before publication leaves only owned staged garbage, no unrelated files affected. Inject ENOSPC, permission, short write, `Interrupted`, EIO, source truncation/replacement, cancellation, cross-device rename and target races. Test same-path hardlink/symlink alias. No-clobber under concurrent builds must use native atomic primitive or fail.
- Compression: each admitted chunk consumes byte credits including worst-case output/workspace; credits released exactly once after output or cancellation; ordered writer emits each admitted successful logical chunk once in correct order; failure cannot publish a partial image; no unbounded queues or waiting with required lock held. Simulate reorder, slow head-of-line, worker panic, output failure, lost worker, canceled producer, insufficient credit, all-zero/raw fallback. Verify serial/parallel equivalence per pinned deterministic profile and real memory accounting; scheduling proof cannot prove codec correctness.
- HFS+ and APFS fresh images: cover every byte, no overlaps except intentional shared extents with modeled ownership, all ranges valid, map counters agree with set-based model, metadata trees well-formed, IDs unique in namespace, all required records resolve, source bytes and metadata exact within declared profile. Prove geometry and allocation separately from native format semantics. Verify independently with native tools.
- HFS+ mutable/journal: old or new metadata state per documented atomic transaction scope, committed changes durable only after required barriers, no crosslinked or dangling reachable allocations, no replay of uncommitted/foreign/out-of-bounds records, no lost unrelated objects; metadata journal does NOT imply old-or-new user data for arbitrary overwrites. Commit/data durability model explicitly distinguishes data vs metadata, ordered data requirements and failure semantics. Double replay idempotent; crash after partial replay returns same valid state or explicit dirty error. Refuse writes for unsupported journal/profile.
- APFS mutable/CoW: no published checkpoint references unpersisted blocks; active checkpoint/root and maps resolve consistently at selected XID; old checkpoint/snapshot/clone blocks never freed before their final required references disappear; space accounting separates reachable, retired/pinned, deferred free and free. Commit publication after complete persistent object graph; crash recovers a qualified complete old/new checkpoint, not mixed tree. Test XID rollover bounds, ring wrap, torn descriptors, delayed reclamation, snapshots/clones spanning transactions and second crash in recovery. Actual order derived from format/native qualification, not from model alone.
- Extraction/install: destination rooted in authorized directory using handle-based race-resistant path resolution; no external symlink/parent/reparse escape; collision never overwrites without explicit permission; stage per published unit, preserve old destination on failure where supported; report multi-item partial completion, no false transaction guarantee across unrelated paths. Preserve files/forks/attrs or reject/report explicitly. Verify app copy against source manifest; never run image content. Mount/eject: auto-eject requires verified fresh intended copies and same managed mount identity; preexisting identical app, partial writes, stale/lost events, busy mount and cancel are negative cases. No force-detach; no eject merely from quiet period. Native platform tests essential.
- Remote/release/MCP: mock HTTP 206/200/416, changed validators, missing/lying lengths, redirect, timeout, reordering, retries, malformed notarization response, interrupted submission, stale digest, rejected ticket, unauthorized roots and changed inputs. Require strong snapshot validator for multi-range integrity or explicitly snapshot full source, not weak metadata heuristic. Toxiproxy only on loopback test services; wiremock for response semantics; real Apple service only protected credentials. State transitions never sign/overwrite/mount outside authorized intent; no claims of native trust from mocked tests.

## 6. Test corpus, differential and metamorphic strategy

Each fixture has origin/provenance, generator script/commands/version, original input manifest, expected semantic facts, geometry/profile, hash, redistribution approval and required oracle versions. Include minimal handwritten independent binary examples, native-generated tiny/multi-file/multi-volume, adversarial malformed structures, large generated datasets (no giant binary Git files), minimized fuzz failures. Pin native OS build/architecture; use Sequoia initially plus supported macOS releases as available. Native checker and parser reference often have different coverage; unsupported is not pass. Compare logical bytes/forks, name semantics, xattrs, hard-link groups, symlinks, timestamps with representable precision, permission/flags, allocation facts, checksum domains and Finder behavior; never reduce to just filename/size. Independent checksum or allocation ledger computed from specification or separately generated native facts. Compare decoded raw bytes of native UDIF conversions; signed image validation native, no stale signatures. Test native output read by us, our output read by native and independent implementations, and independent output read by us. Round-trip supplemental only. Regression golden data normalized to remove irrelevant host timestamps but retain raw artifacts/digests for audit. Use metamorphic tests: splitting reads vs contiguous, permuting input insertion order when semantics canonical, serial vs parallel output, compression changes preserve logical sectors, raw vs wrapped equivalence, no-op edits preserve unaffected objects, cache warm vs cold, snapshot reads unaffected by new transactions. User-supplied DMGs untrusted: no automatic mount/launch during inspection; native tests only owned/synthetic or isolated approved fixtures.

Fuzz targets for each entry point: one target per relevant structure and integrated readers, parser -> verifier, build from structured manifests, decoding and resource limits, path/metadata, object/extent lookups. Seed native and generated valid fixtures, dictionary magic/record types; add structured generators, truncation at every offset for small images, bit flips, integer maxima, huge claimed size, cycles, invalid flags, zero runs, count/length disagreement and decompression bombs. Cap time/memory/file size and recursion; detect hangs/timeouts. Do not filter invalid inputs just because they are hard to handle. Crash corpus replay in PR, minimize & add deterministic regression and semantic assertion. No crashes/hangs/unsafe escapes in required corpus. Scheduled fuzz initially >= 30 min per active critical target, release >= 2h per critical target across accumulated dedicated runs (record seed/time/coverage, resource allocation; raise for mature releases). Smoke 15-60s per touched target subject to CI budget; run full corpus replay regardless. Time thresholds are proposed engineering policy, not a proof or statistically guaranteed absence of bugs.

## 7. CI and quantitative gates

| Lane | Required checks / disposition |
|---|---|
| Local | fmt check, relevant Clippy, nextest, unit/property subset, architecture + 500-line policy, fixture replay |
| PR | fmt, Clippy -D warnings for owned targets, nextest, doctest, property/state-machine tests, coverage, no-default/default/selected feature checks; exact changed proof gates; fuzz smoke/corpus; architecture and dependency license/advisory/secrets checks; native supported-profile tests on protected synthetic runners when changed |
| Scheduled | extended fuzz, Miri, cargo-mutants, broader Kani/Lean/TLC, Shuttle/Loom, exhaustive fault schedules where tractable, Toxiproxy for network features, Criterion controlled baseline |
| Release | clean pinned build, all advertised profile and feature combinations, independent/native matrix and signature tests, full corpus, activated proof gates, fault injection for affected features, reviewed mutation/coverage evidence, SBOM/license notices and evidence bundle |
| Proof-sensitive | source/feature/assumption/dependency/toolchain change invalidates corresponding evidence; regenerate extraction, recheck proofs/model + actual tests before merging or publishing affected capability |

Proposed initial quantitative thresholds: owned critical format/geometry/allocator/planner/transaction modules >=95% lines and >=90% branches where tool reports meaningful branch coverage; workspace owned logic >=85% lines; no untested error branch for declared safety invariants, review coverage changes rather than blanket exclusions. Generated code, UI renderer/platform-only code and test harness metrics separate; collect target-specific coverage, do not combine to hide untested code. If branch tooling unavailable use named branch/condition catalog with explicit test obligations, not fake percentages. All safety-critical mutants killed or documented equivalent/nonreachable with review; target >=90% killed of remaining viable mutants in critical modules, >=80% other targeted logic. Timeouts are not kills by default; classify separately. Establish baselines before enforcing performance thresholds; use controlled runner median/p95 (sufficient samples), peak RSS/owned working set, temp bytes, throughput, output size; report >10% wall-time or >1% deterministic size changes for review and enforce explicit budget invariants. No unsupported format profile receives a passing label from code coverage. Record any exception with owner, reason, affected profile, expiry, alternative evidence and approver; no exception to known data corruption, escape, secrets, invalid signature claims, failed proof for activated gate, or required native validation.

## 8. Supply-chain and architecture assurance (Euclid adapted)

- `cargo-deny` (licenses, advisories, sources/bans), `cargo-audit`, evaluate `cargo-vet` for highest-risk dependencies, Renovate controlled version PRs, Gitleaks secret scan, Trivy or equivalent SBOM/vulnerability scan, optional centralized SonarQube Server for quality/security reports; report actual supported Rust analyzer coverage, not substitute for executable gates. `sccache` for development and CI caches keyed by toolchain/lockfile; no cross-trust sharing of executable caches. Pin CI actions by immutable commit, restrict permissions, separate untrusted PR from release/Apple credentials. Generate SPDX/CycloneDX SBOM, dependency license and provenance inventory for each distributed profile. Hash and sign artifacts in protected release workflow. Test dependencies/oracles separate from normal graph; no core `fstool`, `udif`, `apple-dmg`; optional signing transitive exception explicit.
- Deterministic workspace checker built in `xtask` from `cargo metadata`: allowed first-party edges, no app -> app or library -> app, no UI/OS/remote/signing in format/core, no dmgez/Charles in independent filesystem repos, no unrelated filesystems/codecs in defaults, host-target conditional dependencies, no proof/testing libs in runtime profiles, permitted default closure and forbidden crates including transitive paths. Check source-tree boundary, 500-line rule + exception register. Verify actual Cargo graph per target/features and negative checks, not only documentation. No arbitrary architecture bypass in agent instructions. For default no Apple commands use sandboxed subprocess audit/controlled PATH; tests and native optional adapters explicit.
- Strict source provenance and IP policy: own implementation, lawful fixture generation, license review for copied/adapted code and Unicode data; no Apple-proprietary source/assets or redistributed full OS images. Reference implementations not trusted as authorities merely by agreement. Review advanced APFS patents and security scope before release; no legal clearance implied by proofs.

## 9. Rollout and non-negotiable release policy

Before any MVP: harness + native fixture generation, checked code units, unit/property/negative/fuzz/corpus/differential tests, deterministic architecture/dependency checks; Kani pilot on critical range/offset calculations before admitting hostile input; explicit plan for every invariant. Before builder release: sealed range coverage, tree/alloc invariants, deterministic parallel order, cancellation and publication failure injection, native attach/fsck and metadata comparisons. After MVP: expand Kani, implementation-linked Lean, TLA+ and mutation evidence on the staged gates in each catalog; do not require complete whole-program proof before usable immutable builder. Before real mounts, auto-eject, remote/signing and any mutable filesystem profile: prove/model/test registered protocol obligations and run actual platform/driver/device qualification. No general-purpose writable filesystem claim on the strength of immutable constructor tests. No unsupported capability needs to delay an independent release; remove or disable it and report evidence gaps. A failed verification is a blocker for its required scope, never renamed to skipped. Release evidence is stronger than a design review score. This pack contains proposed specifications and bounded abstract reference-model examples only; no implementation-linked proof, actual filesystem conformance, performance benchmark, CI or security certification has been run.

## EES-1 revision 3 portability gate
Kernel-facing HFS+/APFS crates have mandatory no_std + alloc target/feature checks from their initial release. Record target, feature graph, toolchain and command evidence for isolated checks/builds on both provisional bare-metal targets. Use identical semantic fixtures in hosted tests for kernel-capable and std configurations. This compilation gate supplements, never replaces, Kani, Lean, TLC, fault injection and native compatibility obligations. Actual Charles kernel safety requires separate allocator, scheduler, VFS, device and persistence tests.
