# Cross-repository contracts (contract revision 0.1 draft)

## C1. Dependency and release boundary

`dmgez` depends on versioned releases of HFS+ (build/read features separately) and, eventually, APFS. HFS+ and APFS never depend on each other, dmgez or Charles. There is no mandatory fourth repository. Start with analogous narrow interfaces in the two filesystem libraries, then extract a neutral block-I/O library only if real consumers and a stable abstraction justify it. dmgez adapts the interfaces, not vice versa. No filesystem type embeds a UDIF run, Finder layout, platform file handle, GUI widget, or TOML representation. No platform-specific filesystem service is required for image generation. Use explicit protocol/revision metadata at boundaries; do not ship Git-branch dependencies as production releases. During development an ignored local Cargo patch may point to adjacent checkouts; CI tests pinned commits until registry releases are qualified. Registry facade names may be occupied; check availability before publishing, and use distinct organization/project-qualified package names if necessary. Repository names remain `dmgez`, `hfsplus`, `apfs`.

## C2. Logical storage, offset units and ownership

Use a byte-addressed, finite, immutable random-access source for reading. A generic trait can be implementable over raw files, bounded partition windows, memory, virtual sectors, or cached HTTP. The signatures below specify behavior, not a shared compiled crate or fixed Rust syntax. Keep on-disk geometry separate from transport alignment.

```rust
pub trait ReadAt {
    type Error;
    fn len(&self) -> u64;
    fn read_exact_at(&self, offset: u64, dst: &mut [u8]) -> Result<(), Self::Error>;
}
pub trait MutableDevice: ReadAt {
    fn write_all_at(&mut self, offset: u64, src: &[u8]) -> Result<(), Self::Error>;
    fn sync_data(&mut self) -> Result<(), Self::Error>;
    fn sync_metadata(&mut self) -> Result<(), Self::Error>;
}
```

These traits are sketches: the filesystem-owned error type wraps I/O and typed format errors. Contract: checked `offset + len <= device.len`, no silent short I/O, offset 0 is the beginning of the bounded device, read-only sources never mutate, no shared `Seek` cursor without synchronization, and no implicit sparse zero-fill on read failure. Empty reads at EOF are legal; nonempty out-of-bounds reads fail. A source that changes underneath a reader must report `SourceChanged` or be explicitly documented as a live, inconsistent observation; never use that mode for verification. `ReadAt` need not globally require `Send + Sync`; parallel users require thread-safe adapters or serialized access. Physical block writes must satisfy the device's real alignment and persistence guarantees. A sector view may translate 512-byte logical UDIF sectors into arbitrary file byte ranges, while HFS+ allocation blocks and APFS block sizes remain independent. Checked `u64` offsets; checked `usize` conversion only after resource admission. Newtypes `ByteOffset`, `ByteLen`, `SectorIndex`, `SectorCount`, `AllocationBlock`, `ContainerBlock`, `ObjectId`, `TransactionId` should prevent unit and namespace confusion. Partition windows validate all relative ranges; nested views cannot escape the parent. `sync_*` semantics must be backed by actual device barriers before claiming crash consistency; `std` adapters are not proof of a hardware flush guarantee.

## C3. Build plan contract: immutable sector image

Filesystem constructors return a sealed plan with immutable geometry, stable object IDs, all metadata and explicit source extents. A plan exposes `image_len()`, `read_exact_at()`, `write_to(sink)`, and, where practical, `iter_ranges()` that labels known-zero ranges. Data references are capability-bound reopenable handles or a controlled snapshot, not arbitrary strings dereferenced later. Both builders expose logical sector generation without a full-sized raw image. Each range is either an owned metadata payload, source data slice (including resource forks), or an intentional zero region. Every range must be nonoverlapping and cover the image exactly; source mutation, unsupported lengths, or short reads abort. Default build may hold a metadata index proportional to entry count; cap entries and metadata bytes separately from payload memory; offer a budgeted metadata spool only when implemented. No claim of constant total memory irrespective of file count. Plans can read concurrently if their sources allow it; a single output writer emits deterministic order. Raw image serialization works without dmgez. A filesystem plan has no concept of compression or DMG signatures.

Finder dependency ordering is important: resolve names and stable IDs/timestamps first (including reserved generated assets), allocate/bind the volume identity and CNIDs, build `.DS_Store` background aliases using those final identities, finalize generated byte lengths, then freeze allocation. Avoid changing CNIDs when generated lengths change. If a specific alias needs geometry not yet known, use a fixed-point pass with a strict iteration cap and fail if not stable; do not fabricate an ID. A `PlanDraft` supports metadata finalization, a `SealedPlan` supports reads only. Builder fixtures verify the alias points to the actual background inside the final mounted volume.

## C4. Portable tree and metadata

A filesystem input tree contains stable entry IDs, parent IDs, names in a lossless domain representation, object kind, optional metadata values, regular data and resource-fork streams, symlink target bytes (never followed during packaging), hard-link groups keyed by reliable source identity, and attribute streams. The filesystem owns name comparison, reserved-name rules, encoding and collision checks. Do not rely on host `PathBuf` normalization, generic Unicode normalization or locale lowercasing to implement Apple formats. In dmgez, virtual paths are absolute slash-delimited paths relative to a selected volume, not host paths. Internal node IDs can address names not expressible as UTF-8 or normal path text. Define `RawName`, `DisplayName`, canonical comparison key and explicit escaping; ambiguous representations are errors. User paths are validated without traversing symlinks. Root directory and volume name are distinct. Do not accept special device nodes, sockets, FIFOs or arbitrary internal private metadata namespace through a normal manifest.

Represent metadata as `Known(value)`, `Unavailable(reason)`, or `NotApplicable`, not an empty value for missing source metadata. Capture type, POSIX mode (including executable bits), uid/gid, create/modify/access/change/backup timestamps where supported, BSD flags, Finder info bytes, extended attributes including ACL encoding when present, file length, resource fork, sparse ranges, and hard-link identity. Timestamp precision and epoch conversion are explicit and checked against format limits. Filesystem-specific opaque fields live in typed extensions; preserve supported unknown bytes when editing only if safe, otherwise refuse or emit a structured loss report with user approval. Distinguish raw file metadata from logical metadata (e.g., resolved HFS hard links or compressed-file representation). Content bytes are not the same as resource forks or xattrs. No general-purpose host path is included in an image except intended symlink target bytes. Cross-platform imports must detect unavailable metadata; a ZIP extracted on Windows may have already lost symlinks, executable modes or Mac xattrs. Offer an explicit portable metadata manifest/AppleDouble import with conflicts checked; never guess an executable bit based on extension. The strict packaging policy fails if required metadata cannot be represented or retrieved; ordinary best-effort use requires visible loss reporting and opt-in per profile. Signed app bundles must not be altered for layout convenience. Extractors preserve metadata with host-specific capabilities and reports; if host cannot represent something, offer explicit sidecar export rather than false fidelity.

## C5. Filesystem read contract

An opened volume provides immutable identity, capability report, root handle, `lookup`, `read_dir` paginated iterator, `stat`, `open_data`, `open_resource`, `list_xattrs`, `read_xattr`, `read_link`, and optional `extents`/internal metadata inspection. Paths resolve within one volume, with no implicit host symlink traversal; selecting a link target is a separate operation with a bounded hop count. Reads return exact bytes or an error; no zero-fill for undecodable compressed data or unknown extents. Distinguish link object from referent, fork logical size from allocation size, and regular zero bytes from known holes. A `VolumeId` includes image identity plus partition and subvolume identity; snapshot views also identify XID. Handles are valid for a specific view, not reusable across changed images. Traversal is iterative/cycle-aware with budgeted pagination. Reader should expose recognized unsupported objects and their typed diagnostics so inspect can show metadata while extraction fails precisely. Only the filesystem library interprets its own B-tree/object formats. dmgez combines filesystem logical extents with UDIF block-map indexes without conflating their offsets.

## C6. Capabilities, errors, cancellation and evidence

Define stable machine-readable error categories: `InvalidFormat`, `Corrupt`, `UnsupportedVariant`, `FeatureNotCompiled`, `BackendUnavailable`, `ResourceLimit`, `SourceChanged`, `MetadataLoss`, `Conflict`, `PermissionDenied`, `Io`, `Cancelled`, `VerificationFailed`, `SecretUnavailable`, and `NeedsApproval`. Errors carry stage, safe location/offset, context and causal chain; redact credentials and untrusted control characters. A capability report distinguishes compiled support, detected format/profile, runtime backend availability, and evidence level. `not_checked`, `unsupported`, `failed`, `passed`, and `unavailable` are distinct. Inspection never implies verification. Return partial reports with diagnostics when safe; verify/build refuse to label incomplete results valid. Resource budgets cover physical and virtual bytes, single compressed and decoded block, parser nesting, entry/run counts, file lengths, traversal, cached bytes, xattr sizes, I/O and time. Budgets configurable; hard arithmetic checks non-negotiable. Shared cancellation token checks at block/file/loop boundaries. Progress events include stage, completed/total when known, bytes and object counts, no fake 100% before commit. Clients control rendering.

## C7. Publishing and integration

An output writer targeting a path stages in the same directory, closes and syncs data, validates requested checks, then commits with platform-appropriate no-clobber or authorized atomic replace. Directory durability depends on filesystem/OS; report its limitations. On failure the old file remains intact where supported; cleanup only owned temporary paths. A caller-owned stream cannot guarantee atomic rollback; a failed stream is invalid and explicitly reported. Never truncate a source that aliases the output. File locks and stable identity mitigate concurrent builds. Signing/stapling happens in staging before publication; artifacts and signatures are immutable once committed. Credentialed Apple tests run only on protected workflows, not untrusted pull requests.

## C8. Provenance and future Charles

Keep format facts and research notes independently sourced; use primary specifications and lawfully generated fixtures. Separate research from implementation when restrictive sources are involved. No proprietary binary redistribution, Apple artwork/fonts, private signing keys, or copied implementation code without an appropriate license. Reference source code is not permission to translate it. Audit dependency license and patent obligations; advanced APFS, crypto and boot work need targeted review. Kernel-facing HFS+/APFS core, format, container, reader and transaction engines must compile without std (`no_std + alloc` as needed) from their first release; no mandatory OS threads, host paths or clock. Bulk builders and platform adapters may use `std`. APFS runs in Charles kernel space; its userspace std port is not a prerequisite. EES-1 section 3a defines compilation and later kernel qualification gates. A no_std build alone does not qualify a kernel driver, and a successful file-format reader does not authorize boot/security compatibility claims.
