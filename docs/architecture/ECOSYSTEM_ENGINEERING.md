# Ecosystem engineering standard (EES-1)

Revision 3 • 2026-11-24 • Applies to dmgez, hfsplus and apfs. EVS-1 remains the verification authority; owning feature specifications define binary behavior. These instructions are mandatory for humans and coding agents. New conventions below supplement the recovered prior project guidance; they do not assert that every earlier project's instructions were available verbatim.

## 1. Operate across all three repositories

Treat the three repositories as one coordinated engineering scope, even when VS Code opens only dmgez or an agent starts in any one checkout. The editor workspace is not the project boundary. At the start of every engineering session, identify the actual Git root (`git rev-parse --show-toplevel`), discover the other two checkouts, and read each repository's AGENTS.md, architecture, roadmap and relevant contracts. Prefer explicit configured paths, then sibling directories of the Git root; verify repository identity from Git remotes and manifests rather than assuming directory names. Do not perform a broad disk search. If a repository is missing, use a verified remote and clone into a permitted sibling directory only when authorized; otherwise report the missing checkout or sandbox permission and continue independent work. Never silently substitute a registry release for a required local integration check.

Expected checkout layout (not a monorepo):

```text
parent/
  dmgez/
  hfsplus/
  apfs/
```

Maintain a single cross-repository task/impact plan. For each task, examine all three repos, determine which contracts, APIs, fixtures, tests, feature flags, documentation and release constraints are affected, and make coordinated changes in every affected repo during the same task. Advance independent workstreams where the task covers multiple repos; do not serialize everything behind dmgez or wait for APFS to finish before HFS+ integration. Do not invent unrelated changes merely to touch all three repos. Record why a repo needs no changes. APFS remains an independent nonblocking track, with read-only work preceding writable features.

Before editing, inspect Git status and existing diffs in each checkout. Preserve user changes, repository history, licenses and local configuration. Use explicit working directories (`git -C <repo>`, `cargo --manifest-path <repo>/Cargo.toml` or per-repo shell cwd); never rely on the editor's cwd. Do not reset, clean, force-push, overwrite uncommitted changes, publish, or elevate privileges without authorization. Use small, focused Conventional Commits with explicit paths. Keep each commit buildable where applicable. Keep separate commits and releases per repo; a coordinated task is not an atomic cross-repository Git commit. Do not create a fourth repo or super-workspace merely to coordinate work.

For local integration, use temporary Cargo patches or equivalent local configuration referencing the actual sibling filesystem checkout; do not commit machine-specific absolute paths or make released packages depend on sibling paths. Record exact revisions and dirty status, feature set, target and toolchain. Test each filesystem independently with raw images; then test dmgez against changed local library versions and against the intended pinned release dependencies. Do not silently publish an integration that has only passed against an unpublished sibling branch. Keep contracts synchronized in all three copies and document compatible version ranges and coordinated release order. Release libraries first when needed; requalify dmgez against published versions. A multi-root VS Code workspace is convenient but not required.

At handoff report each repo's path/revision, changed files or no-change rationale, tests actually run, failures/skips, cross-repo compatibility, and remaining tasks. If one repo is inaccessible, explicitly mark ecosystem qualification incomplete; do not claim all-three success. Execute independent permitted tasks concurrently when useful, with isolated build directories and bounded shared resources. Never manufacture evidence for inaccessible repositories.

## 2. Rust workspace and source conventions

- Rust edition 2024, resolver 3 where supported; pin a stable toolchain and explicit MSRV. Nightly/proof tools use isolated pinned toolchains. Centralize dependency versions, metadata and lints through workspace inheritance; keep lockfiles for reproducible application/workspace CI. Follow semantic versioning and document API changes.
- Executables in `apps/`; crates in `crates/<domain>/<fully-prefixed-package>/`. Use meaningful domain boundaries and one authoritative implementation per responsibility; extract crates for real reuse, ownership, dependency or testing boundaries only. Independently useful libraries live outside dmgez; no dmgez or Charles dependency in HFS+/APFS. No app-to-app or library-to-app edges. Avoid giant core modules and speculative frameworks.
- Use tabs for Rust indentation. Every repository sets `hard_tabs = true` in its root `rustfmt.toml`, and CI checks formatting with that configuration. Follow mandatory indentation rules in formats such as YAML.
- No magic strings or numbers. Give on-disk signatures, record types, flags, field offsets and widths, serialized keys, policy defaults and shared identifiers descriptive typed constants or enums. Put shared wire values beside the owning codec and use the same definitions for parsing and encoding. Keep fixture expectations and ordinary explanatory diagnostics readable at their point of use.
- 500 physical lines per Rust source file by default; enforce via deterministic checker with reviewed per-file exceptions for generated code, tables or cohesive modules. Don't game the limit with artificial splits. Small focused functions and meaningful names; snake_case modules/functions, UpperCamelCase types, SCREAMING_SNAKE_CASE constants; prefer conventional module files and explicit exports. Group standard/core/alloc, third-party and local imports consistently; avoid glob imports in production except reviewed idiomatic cases. Keep visibility private or crate-scoped unless a public API is intentional. No duplicated implementations, dead stubs, untracked TODOs or broad lint suppressions.
- Use typed domain IDs, units, validated newtypes, enums and typestates to make invalid states difficult to represent. Prefer exhaustive matches and explicit conversions; never assume host endian, pointer width or alignment. Use checked arithmetic before allocation/indexing and bounded parsing. Use `Result` and typed library errors (e.g. thiserror when appropriate); application boundary may add context with anyhow. Preserve causal errors and distinguish unsupported, corrupt, resource limit, cancellation and I/O. No unchecked unwrap/expect/index/cast on untrusted paths; internal invariant assertions require justification and tests. No panics as normal error handling. No silent fallbacks that change format semantics.
- Prefer safe Rust; forbid unsafe in pure format/model modules where feasible. Isolate FFI and unsafe in narrow reviewed modules; document every safety invariant, lifetime, ownership, alignment and threading precondition with SAFETY comments and targeted tests. Never transmute hostile bytes into structs. Avoid unsafe or zero-copy tricks without measured benefit. No unnecessary clone, allocation, abstraction or dependencies; use borrowing and explicit ownership where clear, not at the expense of soundness.
- Document public APIs with invariants, units, errors, resource limits, examples and compatibility restrictions; explain why nonobvious code exists, not obvious syntax. Keep docs and code synchronized. Prefer readable idiomatic Rust over cleverness. No blanket allowances to silence Clippy; exceptions scoped and justified. Format with rustfmt; run Clippy with warnings denied on owned targets.

## 3. Runtime and dependency discipline

- Separate pure deterministic planning/state machines from I/O, platform adapters and presentation. Prefer sans-I/O cores; inject clocks, storage, scheduler and external services as needed. HFS+/APFS kernel-facing format, core and filesystem engines must compile without std; see section 3a. Host adapters and bulk builders may use std. No hidden host filesystem, environment or thread dependencies in core. Do not impose Tokio on synchronous format code. Use bounded blocking I/O and Rayon for independent CPU work; no unbounded queues or detached work without lifecycle ownership. Cancellation, backpressure, resource accounting and ordered results are explicit. Prefer single-owner mutable state; don't introduce shared locks, concurrent maps or mmap casually.
- Stream large payloads, use bounded buffers and checked size arithmetic, avoid full-image intermediates for standard builds. Metadata growth must be separately accounted for. Preserve deterministic output across worker counts for the same reproducible profile; stable iteration order and explicit metadata policy. Benchmark with Criterion and representative fixtures before adopting SIMD, allocators, alternative collections or concurrency complexity; measure peak memory, I/O and throughput, not just microbenchmarks. For GUI responsiveness, never block UI thread with long disk/network work.
- Minimal defaults: dmgez build + parallel, no advanced readers/UI/MCP/signing/network/mount/legacy dependencies unless needed by selected capability. Feature flags additive, target-specific dependencies correctly gated; test no-default, default, serial, representative combinations and supported all-features targets. Use cargo metadata/tree and executable architecture checks on actual transitive graphs. Focused libraries acceptable after license/maintenance/compatibility review; no production delegation of native UDIF/HFS+/APFS to reference implementations. Optional signing's transitive apple-dmg exception remains as documented. Pin and audit dependencies, avoid redundant implementations and unnecessary default features. No speculative abstractions or crate proliferation.

## 3a. Kernel execution and standard-library boundary (mandatory)

Charles will execute APFS in kernel space. HFS+ is also intended to be kernel-reusable. Do not depend on Charles's future userspace Rust `std` port to run the filesystem drivers; that port is a separate consumer of kernel services. This is a mandatory design and compilation boundary from the first release of each affected engine crate, not an optional long-term aspiration. It does not require an allocation-free filesystem or a working Charles kernel today.

| Component | Required compilation environment |
|---|---|
| HFS+/APFS on-disk codecs (`*-format`) | `no_std`; `alloc` permitted where needed, prefer allocation-free fixed-width codecs |
| Filesystem core, APFS container/object mapping, readers, mutable writers, journal and transaction logic | `no_std + alloc` |
| Shared allocation, collation, tree, checksum, extent and cache logic used by a kernel engine | `no_std + alloc` |
| Immutable bulk image constructors | `std` permitted; any shared kernel-facing algorithm must retain the above portability |
| Host adapters, CLIs, tests, fixture generators, GUI, MCP, dmgez/UDIF and Rayon pipelines | `std` permitted |

The filesystem libraries may provide a default `std` convenience feature for hosted consumers, but it must be removable. `std` is additive and must not select different on-disk semantics. Use `#![cfg_attr(not(feature = "std"), no_std)]` and explicit `alloc`/`core` imports in dual-mode crates, or unconditional `#![no_std]` for pure crates; use `extern crate alloc` where needed. Use `Vec`, `String`, `Box`, `BTreeMap`, `BTreeSet`, etc. from `alloc`, and `core::error::Error`, checked arithmetic, atomics and formatting from `core`. `Arc` requires supported pointer-width atomics. Use qualified `hashbrown` or other focused no_std dependencies only if justified; inject hash seeds/entropy when needed. Do not recreate the standard library. No default-feature leakage through workspace dependencies; explicitly disable dependency defaults and forward `std` only at hosted boundaries. Qualify codec, crypto and other optional features per target before enabling them in a kernel-capable profile; hosted-only optional features must be labeled and kept out of that profile. `--all-features` on a host is not a kernel profile.

Kernel services are supplied by explicit adapters: allocator, block I/O and durability barriers, locks/scheduling/wakeup, clock, entropy, diagnostics and cache/memory pressure. No `std::fs`, `std::io`, OS threads, host clocks, runtime, OS mutex or process calls in the no_std engine. Keep blocking/async choices outside pure algorithms; no generic spin lock held across blocking I/O. No filesystem code should assume an unlimited heap; preserve bounded metadata/cache budgets and handle fallible allocation where supported, with allocation failure policy explicit. The final kernel binary, not filesystem libraries, owns global allocator and panic policy. No need to introduce a new shared repository solely for these interfaces.

### Mandatory compilation and behavioral gates

- When each affected crate first exists, build it in isolation with defaults disabled and the explicit supported kernel-facing feature set on `aarch64-unknown-none` and `x86_64-unknown-none` (initial provisional Rust bare-metal check targets, not Charles ABI targets). Pin/install target support via the chosen toolchain; do not silently skip either target. An example for an existing crate with no extra feature requirements: `cargo check --locked -p apfs-container --no-default-features --target aarch64-unknown-none`. Repeat per crate/target and explicit feature profile; do not use workspace `--all-features` to substitute for this. Run `cargo build` for the same profile as a release gate, since `check` does not exercise code generation. No host-only build scripts or proc macros may introduce a target-side std dependency; host-side build tools themselves are allowed.
- Inspect target-specific normal dependency feature graphs (`cargo tree --target <target> -e normal,features` with the same package and features; use target-filtered cargo metadata as needed). CI architecture checks enforce forbidden target-side host dependencies and fail on feature leakage. Test no_std engine profiles on a hosted harness with simulated devices, plus the ordinary std profile against the same fixtures and semantic expected outputs; keep test-only std dependencies out of bare-metal production graphs. A host test or host build with defaults off alone is insufficient evidence.
- Record exact commit, toolchain, target, features, dependency graph and command result; failed or unavailable required checks are not passing. Add a minimal bare-metal integration/link harness when actual allocator and platform services exist, followed by Charles-specific VFS/driver, scheduling, concurrency, fault, persistence and memory-pressure qualification on disposable media. Bare-metal compilation is not proof of kernel safety, ABI compatibility or crash consistency. Retain all EVS-1 formal and native interoperability gates.

## 4. Testing, verification and security

Follow EVS-1 and local obligation registries. Required bootstrap/PR tools include fmt, Clippy, nextest, doctests, proptest, cargo-fuzz corpus/smoke, llvm-cov, dependency/architecture and line-limit checks. Scheduled/targeted tools include cargo-mutants, Miri, Loom/Shuttle, Kani, Lean 4/Mathlib production-linked proofs via supported hax or Charon/Aeneas pipelines, TLA+/TLC and deterministic fault-device simulation. Verify actual production algorithms and explicit assumptions/bounds; alternative Verus/Creusot only when appropriate. Never hide failures, weaken tests, change oracle results, reduce proof bounds or accept snapshots to make CI pass. No claim that selected proofs establish whole-product correctness. Native Apple oracles and independent readers are mandatory for advertised compatibility; own round-trip alone is insufficient. Use synthetic redistributable fixtures and preserve minimized failures. Writable filesystems require crash-consistency and native qualification before release.

Use cargo-deny, cargo-audit, selective cargo-vet, Renovate, Gitleaks, Trivy/equivalent SBOM scan, optional SonarQube and sccache as specified by EVS-1. Pin CI actions, isolate secrets and protected native release jobs. Testcontainers/SQLx/Goose/Squawk from Euclid are not mandatory for these non-database projects; use network fault tools when network features exist. Never run destructive tests on real disks or user data. Source provenance and license obligations apply to all adapted code and fixtures. No credentials or proprietary Apple assets in repository or test logs.

## 5. Agent execution and completion

Read owning specifications and actual code before implementing. Prefer small reviewable changes, resolve uncertain format semantics with documented evidence, keep error paths and negative tests as first-class requirements. Never substitute placeholders for working implementations or claim unsupported features. Run relevant tests and proof gates before reporting done; distinguish failed, skipped, not run and passing checks. Report exact commands and limitations. Keep requirement/test/proof IDs stable, update docs and version contracts together, and do not claim a release gate passed until evidence exists. Cross-repository coordination is mandatory even for narrowly scoped work; actual modifications must remain task-relevant.
