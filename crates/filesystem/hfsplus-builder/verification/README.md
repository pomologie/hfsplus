# HFS+ builder verification

The Kani placement harness covers the interval admission portion of H-V07. It checks up to eight placements with arbitrary `u64` offsets and lengths against an independent widened-arithmetic prefix model. It calls the production admission function and reaches a complete nonempty prefix. Kani 0.68.0 and CBMC 6.11.0 verified the harness and reached its cover on macOS arm64. [Admission harness](kani/placement.rs)

The positioned-read property test enumerates all 3,840 combinations of placing five segments in any order with one or two bytes per segment. It checks the sealed range map and compares both sequential emission and every valid positioned request against independently assembled bytes. The cases include explicit zeros, a direct source window, and two slices of the same registered source, all with nonzero source offsets where relevant. EOF-overrun and `u64` endpoint-overflow requests preserve the destination and return distinct typed errors. Run `bash check-positioned-reads.sh` from this directory for the `sealed-positioned-property` release profile. [Positioned-read property test](positioned_reads.rs)

Run `bash check-sealed-faults.sh` for the `sealed-stream-faults` release profile. Its four in-memory tests check propagation of premature EOF, another source error, a detected same-length source identity change, and a sink error. They also check retry at the failed offset and cancellation on both sides of a chunk read. The source reports the identity change through `ReadAt`; the builder propagates it. [Sealed-plan tests](../tests/sealed_plan.rs)

The `sealed-image-differential` release profile checks the independently decoded interleaved image described below. The `sealed-image-native` profile checks the same pinned image with Apple `fsck_hfs -fn` through an unmounted read-only software attachment. The validator requires the no-write result, detach, and unchanged image digest. The canonical native and 7-Zip checks provide separate mounted and independent readback evidence. [Release evidence](../../../../verification/README.md)

The Kani allocation harnesses cover part of H-V06 for volumes with up to 32 blocks, 512-byte and 4096-byte allocation sizes, and any partial device tail below one block. An exact initial reservation can reach any admitted cursor. From that state the transition harnesses compare a full-width `u64` request and resulting free count against an independent `u128` range model. The bitmap harnesses compare every encoded bit at any admitted cursor to the same model. The standalone `bash check-allocation.sh` invocation runs four named harnesses and the `fresh-allocation-kani` release profile requires both covers in each harness. Larger bitmaps and complete native volumes have separate test evidence. [Release evidence](../../../../verification/README.md)

Run `python3 -B check-canonical-volume.py --allocation-differential` to compare the interleaved witness against an independent wire model for H-V06. The model reconstructs block ownership from the reserved regions, special forks, and both complete file extent chains. It requires disjoint, in-volume ownership, identical primary and alternate headers, and exact agreement with all 2,048 bitmap bits and the header's free count. This single witness allocates 2 reserved, 11 metadata, and 80 file blocks and leaves 1,955 free. The four-layout property test and the native free-count comparison use separate fixtures. [Independent allocation oracle](interleaved_allocation_oracle.py)

Install Kani 0.68.0 and run `cargo kani setup` before running `bash check.sh` from this directory.

The read-only native mount reported root CNID `2`, generated CNIDs `16`, `20`, `22`, and shared inode `30` with two links. The mounted payloads agreed with the independent extract. The existing draft test below checks exact object and thread keys against its reference model. The canonical witness kept its pinned digest. [Fixture emitter](../tests/draft_identity.rs)

H-BUILD-01-T02 passed on macOS 14.7.2 arm64 with Rust 1.99.1. The draft test permuted manifest and link-name order, varied the three generated asset lengths after reserving their identities, and exercised every prefix of all six binding orders. ## Exact capacity

H-BUILD-02-T01 passed using the [allocation coverage test](../tests/allocation_coverage.rs) and [native layout runner](check-allocation-layouts.py) on macOS 14.7.2 arm64 with Rust 1.99.1. The empty, small, 3 GiB logical payload, and 100,000-file fixtures emitted volumes of 8,413,184, 8,421,376, 3,229,736,960, and 39,137,280 bytes. The block-set model projects placed metadata and source byte ranges onto allocation blocks, verifies a unique owner per allocated block and accounts for the two reserved header blocks. It compares every modeled bit against the stored allocation bitmap and checks exact coverage, free count, catalog file count, and both headers. Automatic capacity left exactly 8 MiB free in each volume, with explicit-capacity sealing reproducing the same geometry. The small fixture rejected a bound one allocation block below the required capacity. At a fixed block size, usable capacity is monotone because each additional volume block grows its bitmap reservation by at most one block. The binary search halves the remaining range of 32-bit block counts each step and terminates within 32 steps. [Capacity search](../src/volume/capacity.rs)

The `fresh-allocation-property` profile runs only the positive four-layout set comparison. The `fresh-allocation-native` profile independently compares Apple `statvfs` with the canonically pinned image's header. It checks 2,048 total and 2,033 free 4,096-byte blocks on a read-only software mount, detaches it, and verifies the same raw SHA-256 again. The native evidence applies to that single valid fixture and runner. [Release evidence](../../../../verification/README.md)

Apple `fsck_hfs` hfs-650.140.2 completed all four no-write checks on disposable read-only attachments, including catalog, hierarchy, and volume bitmap validation. The checker reported a raw-device permission warning before falling back to the read-only block device. The fixtures define all payload bytes as zero, so the native emitter stores metadata and leaves known zero ranges unbacked in the temporary host file. This preserves the full logical raw volume, including allocated payload blocks. The hosted macOS job runs the native script alongside the canonical witness. Strict Clippy passed for the allocation coverage target.

H-BUILD-02-T02 passed on macOS 14.7.2 arm64 with Rust 1.99.1. The reference block count assigns two blocks to the reserved sectors and headers, one to the allocation bitmap, three to the required tree nodes, and one to data. Exact capacity at seven 4,096-byte blocks produced matching headers at the primary and end-relative offsets. The bitmap marked all seven blocks allocated and the free count was zero. An exact capacity of six blocks failed before producing a sealed plan, with `InsufficientSpace` reporting 28,672 required and 24,576 available bytes. The source fixture would fail the test if capacity selection or sealing read its payload. All six tests in `cargo test --locked --offline -p hfsplus-builder --test volume_capacity` and strict Clippy for that target passed. [Capacity tests](../tests/volume_capacity.rs)

H-BUILD-02-T03 passed with two disposable variants of the native small witness. In one variant, the file data forks of catalog IDs 16 and 17 claim the same two blocks. The reference set finds exactly that intersection, and the allocation bitmap still contains 2,048 free blocks. In the other variant, the file claims remain disjoint and both headers declare 2,049 free blocks while the bitmap still contains 2,048. No-write `fsck_hfs` hfs-650.140.2 rejected both variants on macOS 14.7.2 arm64. It identified both owners of the overlapping extent and reported the exact 2,048 versus 2,049 discrepancy on the counter variant. The clean control and all three other valid layout witnesses passed in the same run. The four H-BUILD-02 acceptance cases are now complete. The broader H-V06 obligation retains its own proof and property evidence. [Reference set and variants](../tests/allocation_coverage/failures.rs) · [Native layout runner](check-allocation-layouts.py)

H-BUILD-02-T04 passed on macOS 14.7.2 arm64 with Rust 1.99.1. A counting source describes a 10 GiB file with three data bytes and known-zero ranges using constant storage. Sealing read zero payload bytes under a 16-placement limit and a metadata budget of 345,088 bytes. The primary and alternate headers matched the reference geometry of 2,621,528 blocks, including 81 bitmap blocks and two free blocks. The volume stores the input as one fully allocated data fork. The evidence covers bounded payload construction from a sparse logical source. `cargo test --locked --offline -p hfsplus-builder --test sparse_source` and strict Clippy for that target passed. The workspace reader matched each directory scan entry against name and thread lookups, reconciled all allocated blocks, and read both forks byte for byte. Tests also verified typed exhaustion of the placement budget, coalescing an unequal tail, and storing a hard-linked file's overflow under its backing inode ID. No-write `fsck_hfs` 650.140.2 checked the overflow file, catalog hierarchy, and allocation bitmap and reported the volume consistent. The native read-only mount matched all 64 directory names and both complete fork payloads. The canonical raw image replay matched its existing pinned SHA-256. ## Canonical raw HFS+ image

The [H-BUILD-05-T01 and T02 fixture](../tests/canonical_volume.rs) emits an 8 MiB clean nonjournaled HFS+ volume with fixed geometry and HFS dates, numeric ownership, and modes. Its synthetic app contains a Unicode guide, two names for one regular file, an inline attribute on that shared file, another inline attribute on the guide, a resource fork, and a relative symlink. The fixture never executes the synthetic app. Reversed manifest, link-name and attribute order must preserve the entire volume.

The [canonical verifier](check-canonical-volume.py) runs the producer in separate processes and checks both outputs against the same pinned SHA-256. The hosted matrix runs this check on Linux, macOS, and Windows. The macOS job also runs the independent and native checks. Run the verifier locally with Python 3.11 or later.

```sh
python3 crates/filesystem/hfsplus-builder/verification/check-canonical-volume.py
```

Pass `--seven-zip 7z` to check the decomposed catalog spelling and exact Unicode file data, symlink bytes, and backing link inode data with an independent reader. Pass `--native-fsck` on macOS to wrap the fixture in a temporary UDRO image and run `fsck_hfs -fn` on a read-only attachment. The native check compares the mounted allocation counts, app tree, ownership, dates, modes and hard-link identity with the expected manifest. It makes a second read-only mount with ownership ignored to compare file data, resource forks, extended attributes and the symbolic-link target under the fixture's restrictive permissions.

On macOS 14.7.2 arm64 (23H311) with Rust 1.99.1, both images from `a1b870f` had SHA-256 `63e2f4d50df05f59a1e6dbe63c77e5d75b10e1e2780bae068af3eec4faeadba6`. p7zip 17.05 matched the three readbacks. `fsck_hfs` reported a raw-device permission warning, completed its no-write checks, and found the volume consistent. The mounted volume matched the header's 2,048 total and 2,033 free 4,096-byte blocks. The normalized native log has SHA-256 `af1e13ce08d5eaaa8eeef4522bd4f1279e4937a552eb982034ec265fe533afc1`.
